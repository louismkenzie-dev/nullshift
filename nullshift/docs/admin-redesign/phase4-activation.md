### `apps/web/lib/billing/activation.ts` — pure rules over the 0064 rows

Builds on `lib/legal/arrangements.ts` (`activationPreconditions`, `chargeability`, `collectionTiming`) and adds what 0064 needs:

- `activationGates(input)` → `{ ok, missing[], charge, contractualStartDate }`. The §8.3 list in the brief's order (accepted current schedule; exact amount/currency/cadence; agreed start; valid collection authority; notice period; service identity; no duplicate rail; internal approval) plus `environment_match`. A **sandbox mandate never satisfies a live activation**; a **held-for-review** or **foreign-tenant** or **replaced** mandate is not authority; a **Xero-native collection workflow** on the same obligation is a duplicate rail even though it is "the same provider", and duplicate rails are reported whether or not a mandate exists yet. `charge` is non-null only when every gate passes and is the accepted snapshot's exact terms, never a catalogue price.
- `dateArrivalOutcome(input)` → `not_due` | `ready` | `exception`. §8.4: once the contractual (or accepted-schedule) start date arrives with any gate missing, the only output is a high-priority owned exception with `plan: null`, `amountMinor: null`, `charge: null`, the original date preserved verbatim, the three resolution options, and a `forbidden` block that is all `false` by type (default plan, indicative charge, backdate, silent date change, forced route change, automatic shutdown).
- `reserveActivation(store, request)` → the one write. Refuses `flag_off` before anything; refuses `gates_missing` before touching the store; inserts a `reserved` row through the `ActivationStore` port; maps 23505 / the index name to `{ ok: false, reason: "duplicate" }`. The store port is what makes two concurrent callers testable in memory and what the server action implements over Supabase. `reservationAuditEntry(result, ctx)` gives the `audit_log` payload for every outcome, including the loser of a race.
- `scheduleActivation(activation, input)` → the `provider.schedule_collection` operation the worker executes (`executeIn: "worker"`, idempotency key `activation:<id>:schedule`, exact amount/currency/cadence, `contractualStartDate` preserved, `requestedChargeDate` = max(contractual start, provider earliest), `providerConfirmedChargeDate: null` until the worker writes it back). No provider call happens here. Only a `reserved` activation can be scheduled; an environment mismatch is refused independently of the gate report.
- `onOtherPaymentArrived(obligation, payment, pending)` → re-evaluates the remaining obligation in integer minor units with an explicit currency. If the pending collection would now over-collect: `request_cancellation` (a worker operation, recorded only on provider confirmation) where the provider permits, otherwise an **urgent owned exception** with `closingPaymentLinkIsInsufficient: true`. Overpayment stays visible with `automaticRefund: false`, `writeOff: false`, `requiresApproval: true`. A currency mismatch is never netted.

### `apps/web/lib/billing/mandates.ts` — mandate records, never subscriptions

- `recordMandateFromEvent(input)` → one `mandates` write plan (insert/update/noop) from **provider-confirmed resource state** (`fetchedAt`, `rawStatus`), never the event body alone. The result carries a `never` block (`createSubscription`, `createActivation`, `scheduleCollection`, `collect` — all `false` by type) and the audit entry repeats it. Provider status mapping is an explicit table (`GOCARDLESS_MANDATE_STATUS`, `STRIPE_MANDATE_STATUS`); an unknown status is held, not guessed. Ordering: a fetch older than `last_provider_sync_at` is a no-op (duplicate / out-of-order delivery); terminal states never regress. Tenant comes from our own records (caller-resolved), never provider metadata, and a bound mandate cannot be re-homed. Consent captured at setup is kept; a later event cannot erase it. Replacement marks the old row `replaced` only once the successor row exists (0064 requires `replaced_by`), otherwise `cancelled` with a follow-up.
- **Orphan mandate**: no tenant → `held_for_review` with reason; no consent evidence → held; a held row stays held until `releaseMandateHold(existing, evidence)` with the client, full consent evidence, a reason and the releasing staff member. Release makes the mandate eligible for the gates; it does not pass them.
- Environment and provider mismatches between an existing row and a resource are refused outright (§12.3).

## Tests — `apps/web/tests/activation.test.ts` (41)

Pure, in-memory; the store fake yields to the event loop then checks-and-commits in one step, like a unique index at commit.

- Flag off: `reserveActivation` and `recordMandateFromEvent` refuse before any store call.
- **Two concurrent reservations → exactly one wins** (and ten → one row); different arrangements do not block each other; missing gate refuses before the store; unique violation recognised by code or index name; audit entry for winner and loser.
- **Date arrives with a missing gate → exception, no charge**: `charge`/`amountMinor`/`plan` null, original date preserved even when today is later, all `forbidden` false; `scheduleActivation` produces no worker operation.
- **Early mandate → no subscription**: fulfilled setup request records `authorised` with the `never` block; authorised mandate before an accepted schedule cannot be reserved; status mapping; unknown status held; later fetch updates, older fetch no-op; cancelled never regresses; replacement needs the successor.
- **Orphan / consent**: held and unusable; a held row stays held; held or foreign-tenant mandate fails `collection_authority`; release requires full evidence.
- **Sandbox mandate cannot satisfy a live activation** at the gate, at `scheduleActivation`, and at the mandate row; sandbox on sandbox passes.
- Xero-native rail is a duplicate rail (named, once), reported before a mandate exists; cancelled and cross-environment rails do not count.
- Scheduling payload: worker-only, contractual date preserved while the requested date moves with provider lead time; only `reserved` can be scheduled.
- Bank transfer before Direct Debit: settle → cancellation requested and recorded only on confirmation; submitted → urgent exception; overpayment visible, never refunded automatically; partial payment leaves the collection alone; currency mismatch is an exception.

## Flags

`billingActivation` (fixed name in `apps/web/lib/flags.ts`). With it off: `reserveActivation` returns `{ ok: false, reason: "flag_off" }` before any store call; `recordMandateFromEvent` and `releaseMandateHold` return `flag_off`. The pure evaluators (`activationGates`, `dateArrivalOutcome`, `scheduleActivation`, `onOtherPaymentArrived`) are flag-free because they perform no I/O and are safe to call from fixtures; nothing in the repo calls them from a live path yet.

## How to try it

There is no UI or route in this task. `pnpm -C apps/web exec vitest run tests/activation.test.ts` exercises every rule. To wire it later: a server action (behind `requireStaff()` and `flagOn("billingActivation")`) implements `ActivationStore.insertReservation` over `service_activations`, writes `reservationAuditEntry(...)` through `logAudit`, and hands `scheduleActivation(...).operation` to the integration outbox; the GoCardless webhook, after signature verification and a resource fetch, passes the fetched state to `recordMandateFromEvent` and persists `plan.row` with the service client plus `plan.audit` via `logAuditAsService`.

## Gaps / not done here / approvals needed

- **No server action or webhook wiring** (not owned): `app/api/gocardless/webhook/route.ts` still creates the subscription on `billing_requests.fulfilled` (Phase 0 §8 #2) — it must be gated to call `recordMandateFromEvent` instead when the flag is on, and the Stripe card rail retired or gated (N-c). The worker that executes `provider.schedule_collection` / `provider.cancel_collection` and writes back `provider_confirmed_charge_date` belongs to the integration-workers task.
- **Tenant resolution for a mandate event** is the caller's job (from `subscriptions.gc_billing_request_id` or an earlier `mandates` row); the fold deliberately refuses to read provider metadata as identity.
- **Exception rows**: `dateArrivalOutcome` and `onOtherPaymentArrived` return exception payloads; persisting them into `finance_exceptions` (0065, kinds `missing_activation_gate` / `duplicate_warning`, severity `urgent`) is the finance-exceptions task's writer.
- **Obligation linkage**: `service_activations` does not yet reference `billing_obligations` (0062) — the service-period obligation is minted by the ledger task; the activation's `schedule_id` is the join for now.
- **Decisions still open** (Phase 0 §9): 18.5 (who pays during the gap), 18.7 (billing unit for multi-system clients — the per-arrangement guard supports either answer), 18.9 (initial mandate timing and charge notice against provider docs; `providerLeadDays` is an input, not a constant), N-i (Suffolk Tennis' open billing request is never touched automatically).

RLS is staff-only; if a client-facing "collection expected on" date is wanted it must be projected by server code, not by opening the table to tenant members.
- Consent wording for early mandate setup (§8.3 step 4) is a solicitor/approval item; `consent_terms_version` is where it is recorded.
