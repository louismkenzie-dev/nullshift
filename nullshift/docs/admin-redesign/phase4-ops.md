Everything here is OFF unless `OPS_V2_FLAGS` contains `integrationWorkers`. The migration is NOT applied. With the flag off the GoCardless webhook runs the legacy handler byte-for-byte (the branch is one `if` at the top of `POST`), the new cron answers `{ ok: true, skipped: "flag_off" }` and touches nothing, and no code path reads or writes the new tables.

### Handlers (`defaultHandlers()`)

| Kind                             | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `xero.create_invoice`            | Reads the invoice; already has a Xero id → done. **Looks the invoice up in Xero by our reference before creating** (`GET /Invoices?where=Reference==…`, same reference format as `lib/xeroSync.ts` so invoices the legacy sync created are found too); found → saves the id (`ops.xero_invoice_recovered`) and never creates. Otherwise contact → create → save id (`setInvoiceXeroId` only writes when null). Nothing about payments. `ProviderError` outage → retry; rejected/unconfigured → dead-letter.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `xero.allocate_payment`          | Reads the allocation; already marked recorded → done; kind ≠ payment → permanent failure (a credit note / refund needs its own approved operation); no issued invoice → permanent failure with a `balance_mismatch` exception. **Invoice not in Xero yet → enqueues `xero.create_invoice` (idempotent) and retries only itself.** Recovery lookup: the Xero invoice's `Payments[]` matched by Reference (= provider payment ref) or, failing that, by amount + date not already claimed by a sibling allocation; a match is adopted (`recovered: true`), never re-entered. Then `recordPayment` and the marker (`evidence.xero_payment_id`, `xero_recorded_at`).                                                                                                                                                                                                                                                                                                                                    |
| `gocardless.schedule_activation` | Payload = the activation lib's `provider.schedule_collection` operation (key `activation:<id>:schedule`). Refuses an operation whose environment differs from the worker's port. Already `active` with a provider ref → done. **Re-runs `activationGates` on every attempt against fresh data**; any missing gate is a permanent failure with a `missing_activation_gate` exception, never a retry. The payload must still equal the accepted schedule (amount, currency, cadence, contractual start; requested date ≥ contractual start) or it is refused. Only then: `reserved` → `scheduled` (requested date, `scheduled_at`), then `createSubscription` with `start_date`, the outbox key as Idempotency-Key and 409 adoption; the provider resource is read back and the **provider-confirmed charge date** is written to `provider_confirmed_charge_date`; amount/currency mismatch or a confirmed date before the contractual start is an urgent `duplicate_warning`. Then `active` + audit. |
| `gocardless.cancel_pending`      | Reads the collection; `cancelled` → recorded as confirmed; `pending_*` → cancel, then **re-read and record only when the provider reports `cancelled`**, else retry; `submitted` / `confirmed` / `paid_out` → permanent failure with an **urgent `duplicate_warning`** ("closing a payment link is insufficient; no refund or write-off without approval").                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `notify`                         | No real send. The outbox key (`notify:<dedupeKey>`) is the dedupe; the port stub returns `{ delivered: false, stubbed: true }` and the run is audited (`ops.notify_stubbed`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

Dead-letter → exception kind mapping: `xero.*` → `xero_outage` with safe retry `xero_create_invoice` / `xero_allocate_payment`; `gocardless.schedule_activation` → `missing_activation_gate` (no safe retry — re-approval is a person's decision); `gocardless.cancel_pending` → `duplicate_warning`, urgent; `notify` → `other`. A handler can override with an `ExceptionHint`.

### Webhook (`apps/web/app/api/gocardless/webhook/route.ts`)

The only change to the route is at the top of `POST`: `if (flagOn("integrationWorkers")) return handleGoCardlessWebhookInbox(req);` plus two imports. Everything below is byte-for-byte the legacy handler.

With the flag on, `processGoCardlessEvent` derives state from **authoritative resource reads**, so confirmed / failed / paid_out delivered in any order converge and a redelivery finds its work done:

- `billing_requests.*` → fetch the billing request and its mandate → `recordMandateFromEvent` (mandates lib) → ONE `mandates` row. **Never a subscription, never an activation.** Tenant is resolved from OUR records (`resolveMandateOwner`: an earlier mandates row, else a legacy pending row); provider metadata is never identity. A held mandate (orphan / no consent) opens `missing_consent`. A **legacy pending row** (`arrangement_id null`, `gc_billing_request_id` matched) is NOT activated: an owned `missing_activation_gate` exception and a stub notify say so (Phase 0 N-i: never automatic).
- `mandates.*` → fetch the mandate → mandate row (terminal states sticky; `replaced` only with the successor row). Legacy mirror: `replaced` follows the new id, terminal states cancel legacy rows exactly as today. A live activation bound to a dead mandate → owned `cancelled_mandate` exception (urgent when active).
- `subscriptions.cancelled|finished` → legacy rows cancelled as today; a new-model activation with that provider ref is marked `cancelled` and audited.
- `payments.*` → fetch the payment. `confirmed` / `paid_out` → ONE `provider_payments` row (unique per provider + ref + kind) and ONE `payment_allocations` row against the service-period obligation that covers the charge date (unique per provider + ref + kind + obligation; the 0062 ceiling trigger is emulated in the memory store), then `xero.create_invoice` (if needed) and `xero.allocate_payment` are enqueued as separate operations. No obligation → `balance_mismatch` exception with the money still recorded. `failed` / `charged_back` after a recorded payment → a typed `bank_return` / `chargeback` provider payment + allocation against the SAME obligation (never a deletion) plus an urgent `failed_collection` exception; with no prior payment → a normal `failed_collection` exception and nothing moves. Legacy rows: `past_due` / recovered and `recordCarePlanPayment` exactly as today. Unmatched money is recorded with no tenant and an `other` exception ("Unmatched Direct Debit collection").
- Environment is part of every lookup: a sandbox event only ever sees sandbox mandates / activations / provider payments, and a processor whose port is the other environment refuses the event.

Transient processing failures leave the event `failed` with a sanitised error; the cron sweeps `received` / `failed` events that are at least two minutes old within the last seven days (bounded to 50).

### Cron `apps/web/app/api/cron/ops-worker/route.ts` + `vercel.json`

Guarded exactly like the other cron routes (`Authorization: Bearer <CRON_SECRET>` or 401). Flag off → `{ ok: true, skipped: "flag_off" }`. Otherwise: sweep the inbox, then `runOnce` with the live ports, `limit: 25`, owner `cron:<deployment>:<random>`. `vercel.json` gains one entry: `/api/cron/ops-worker` every 10 minutes (only the `crons` array was edited).

### `apps/web/lib/xeroOps.ts`

`liveXeroPort()` over `packages/billing/src/xero.ts` (contact, create, online URL, record payment) plus the two recovery lookups (`findXeroInvoiceByReference`, `listXeroInvoicePayments`) and `sanitiseXeroError` (token-free, bounded, classified by status: 429/5xx/network → outage, other 4xx → rejected). The lookups need a bearer token that `xero.ts` keeps private, so this file performs its own client-credentials exchange against the same env vars. packages/billing is not edited.

## Tests — `apps/web/tests/integration-ops.test.ts` (25)

In-memory store and fake providers; no real provider call, no database.

- **Flag off**: capture, enqueue and runOnce all refuse before any store call.
- **Duplicate delivery** → one capture, one processing, one provider payment, one allocation, one create + one allocate operation; the same event id in the other environment is a different event.
- **Out-of-order** paid_out / confirmed / failed / confirmed → exactly one payment allocation, no failed-collection exception (the stale event cannot reverse the newer valid outcome); a genuine late failure after a recorded payment → typed `bank_return` against the same obligation + urgent exception, and a redelivered `confirmed` adds nothing.
- **Crash after remote create** (Xero invoice): retry finds it by reference, one create total, id saved, `ops.xero_invoice_recovered` audited. (GoCardless subscription): retry adopts via Idempotency-Key, one create total, activation `active` with the provider-confirmed date, contractual start preserved.
- **Xero outage**: money recorded and accounting queued (client flow safe); backoff 1, 2, 4, 8 min …; dead-letter after 8 attempts with `attempts = 8`, a `xero_outage` exception carrying `xero_create_invoice` as the safe retry and the idempotency key as `external_ref`; zero GoCardless creates, still one provider payment and one allocation.
- **Allocation-only retry**: invoice already synced, PUT lands but the marker save crashes → the retry recovers the Xero payment (no second PUT, no create); invoice not yet in Xero → the allocation queues the create and both then succeed in order.
- **Lease expiry**: B cannot claim inside A's lease; after expiry B claims (attempts 2); A's late completion is refused; a hanging handler is bounded by attempts-at-claim and dead-lettered.
- **Sandbox isolation**: a sandbox payment event carrying a live subscription ref cannot touch the live activation or obligation (money lands unmatched in the sandbox environment); a sandbox schedule operation is refused by a live worker with no provider call; a live event is refused by a sandbox processor.
- **billing_requests.fulfilled**: mandate recorded (our records decide the tenant, not provider metadata), no subscription, legacy pending row untouched + owned exception; redelivery converges. Orphan mandate held.
- **mandates.cancelled**: legacy row cancelled as today; live activation → urgent owned exception.
- **cancel_pending**: pending → cancelled and recorded only after re-read; submitted → urgent `duplicate_warning`.
- **schedule_activation gates**: a mandate cancelled between approval and the run → dead-letter, no provider call, activation stays `reserved`; a drifted amount is refused before any call.
- notify dedupe; sweep grace period and bound; error sanitising; dead-letter exception mapping.

## Flags

`integrationWorkers` (fixed name in `apps/web/lib/flags.ts`) gates the webhook branch, `capture`, `enqueue`, `runOnce`, `processGoCardlessEvent` and the cron. Mandate recording inside the inbox additionally needs `billingActivation` (the mandates lib's own gate): with `integrationWorkers` on and `billingActivation` off, a `billing_requests` / `mandates` event is captured, then left `failed` with the message "billingActivation is off: mandate not recorded" for the sweep to retry — **enable the two flags together** on any environment that receives GoCardless webhooks.

## How to try it

No UI in this task. `pnpm -C apps/web exec vitest run tests/integration-ops.test.ts` exercises every rule with the fakes. On a preview environment with 0062–0065 applied to a branch database and `OPS_V2_FLAGS=integrationWorkers,billingActivation`: point a **sandbox** GoCardless webhook at `/api/gocardless/webhook`, watch `integration_events` fill and `integration_operations` drain on `GET /api/cron/ops-worker` (with the cron secret); `finance_exceptions` shows anything dead-lettered with its correlation id. Never point a live GoCardless environment at a flagged deployment before the approvals below.

## Gaps / not done here / approvals needed

- **Approval before enabling in production**: with the flag on, a `billing_requests.fulfilled` for a legacy pending row (Suffolk Tennis' open billing request, N-i) no longer creates the subscription; it records the mandate, holds it (legacy setups carry no consent evidence) and opens an exception for a person. That is the brief's rule (§3.3 #2) but it changes a live legacy flow — the owner must confirm it, or resolve N-i first.
- **Stripe webhook** is not migrated to the inbox; `stripe_events` and `app/api/stripe/webhook` are untouched (`integration_events.provider` already admits `stripe`).
- **Xero payment Reference**: `packages/billing/src/xero.ts`'s `recordXeroPayment` sets no Reference, so the allocation recovery lookup also matches on amount + date (bounded by sibling allocations). Adding `Reference` to that PUT (one line in packages/billing, not owned here) makes the recovery exact. Likewise `findXeroInvoiceByReference` / `listXeroInvoicePayments` and the GoCardless mandate/subscription reads and start-dated create belong in packages/billing eventually; they live in `lib/xeroOps.ts` and `lib/integrations/gocardlessClient.ts` for now.
- **Xero tax mapping** (18.8): the create still goes through `createXeroInvoice`'s `NoTax` / `XERO_TAX_TYPE` defaults; the obligation's tax snapshot is not yet projected into Xero line tax types.
- **Who enqueues `gocardless.schedule_activation`**: the staff approval action that calls `reserveActivation` → `scheduleActivation` → `enqueue(opScheduleActivation(...))` is the activation task's server action, not built here. `onOtherPaymentArrived(...).action.operation` → `opCancelPending` likewise needs a caller (bank-transfer recording in the ledger task).
- **Staff visibility**: run history / dead letters are only in the tables (service-role RLS). The Ops › Automations "Run history" tab should read them through a server component with the service client; no staff policy was added (18.11).
- **`provider_payments` environment spelling** differs between 0062 (`test|live`) and 0063/0064 (`sandbox|live`); the store maps it. Aligning the vocabularies is a one-line CHECK change in a later migration.
- **Exception rows from the inbox carry no `created_by`** (service role, no user) — the 0065 column is nullable, so fine, but the queue should show "system: inbox" for them.
- **`after()` on Vercel** runs within the route's `maxDuration`; a very large webhook batch is processed by the cron sweep instead (grace 2 min, bound 50). Fine for GoCardless volumes; note for Stripe later.
- Applying 0063 needs the ledger check (N-h). Rollback is in the header.
