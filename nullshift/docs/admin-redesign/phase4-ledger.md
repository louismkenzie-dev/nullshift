# Phase 4 — Billing obligations, payment allocations, reconciliation and finance exceptions (task p4-ledger)

Date: 2026-09-17. Branch `feat/admin-redesign`. Brief §3.3 #5 (one build invoice per project), #6 (Xero remote-create/local-save window), #7 (reconciliation on page open); §5.6 Finance (Invoices, Collections, Reconciliation, Exceptions); §10.1 ownership of facts and "one commercial obligation has one stable identity"; §10.3 Xero improvements; §12.3 monetary invariants; §14.2 additive rollout ("dropping the old index without a replacement is not an acceptable fix"); §17.2 rows on milestones, rounding, partial payments, reconciliation and mark-paid. Phase 0 report §3 (no obligation, allocation, payout or bank-match concept exists; `0013` partial unique), §7, §8 #5–#7, §9 decisions 18.3 / 18.8 / 18.10 / N-h, §11 live ledger.

Everything here is **off by default**. With `OPS_V2_FLAGS` not containing `billingActivation`, every server action returns `{ ok: false, reason: "flag_off" }` before touching the database, neither migration is applied, and no existing code path reads the new tables or the new `invoices.obligation_id` column. No provider is called anywhere in this task: nothing issues an invoice, records a payment at Xero, schedules or cancels a collection, sends an email or touches GoCardless / Stripe. Amy / The Dance Exclusive, Suffolk Tennis and New Future Therapy are not referenced; the only thing the migration would do to their rows is give each live legacy build invoice an obligation identity (see backfill), with amount, status, provider ids and dates untouched.

### `apps/web/lib/billing/allocation.ts` — pure integer money rules

| Function                                                      | Rule                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `allocateMilestones(totalMinor, shares[{key,label,percent}])` | Percent → basis points once; each milestone gets `floor(total × bps / 10000)`; leftover pennies go one each to the largest fractional remainders, ties to the earliest milestone. Sum equals the total exactly, every time, deterministically. Refuses non-integer totals, percentages ≠ 100.00, duplicate or malformed keys. |
| `applyTax(netMinor, {codeRef, rateBps})`                      | Half-up integer rounding; gross = net + tax. `PENDING_TAX` = `{ codeRef: 'pending_decision', rateBps: 0 }`; `isTaxPending`.                                                                                                                                                                                                   |
| `floorToStep(amount, step, minimum)`                          | Floor to a step, never below the configured minimum (§17.2).                                                                                                                                                                                                                                                                  |
| `spreadPayment(paymentMinor, currency, debts)`                | One payment across several open obligations in due-date order; never exceeds the payment or any debt; leftover reported as `unallocatedMinor` (overpayment stays visible). Refuses a currency mismatch.                                                                                                                       |
| `allocationCeiling(recorded, existing, proposed)`             | The trigger's rule in TypeScript so the UI refuses before a round trip: same-kind allocations of one provider payment cannot exceed its recorded amount.                                                                                                                                                                      |

### `apps/web/lib/billing/reconciliation.ts` — pure payout and matching rules

| Function                               | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payoutArithmetic` / `reconcilePayout` | gross − refunds − fees + signed adjustments = net. Verdicts: `balanced` (arithmetic = provider = bank), `bank_pending`, `bank_mismatch` (amount or currency), `provider_mismatch`, `unstated`. Differences are reported with their sign and never absorbed; every non-balanced-with-evidence verdict except `bank_pending` / `unstated` requires human review.                                                                                                                                                                                                                                                                                                        |
| `suggestMatch(receipt, candidates)`    | Rules in order: currency and (when known) client must agree → remittance reference names obligations (exact → high; under → high partial with the remainder stated; over → ambiguous, surplus visible) → exact single remaining balance (unique → high; several → ambiguous with alternatives; a split transfer's second half lands here) → unique subset sum ("several invoices in one transfer" → high; several subsets → ambiguous listing every combination) → single open debt and under → ambiguous "confirm partial" → none. Every result carries `evidence[]`; every non-high result has `requiresHumanReview: true`. Nothing is ever applied by this module. |
| `checkPayoutAllocations`               | Allocations against a payout can never exceed its gross.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Gaps

1. **No UI yet.** The Finance › Invoices / Reconciliation / Exceptions prototype pages under `/admin/next/finance` still render from `lib/next/fixtures-finance.ts`. Wiring them to `obligationBalance`, `suggestMatch` and the exception actions behind the flag is a follow-on (and needs a `loading.tsx` / `error.tsx` / empty-state pass at that point).
2. **Recording a manual payment / bank transfer** (a `provider_payments` row + `payment_allocations` rows through a staff action) is not in this task. The mark-paid path in `apps/web/lib/markInvoicePaid.ts` is untouched; §17.2 "mark-paid plus link-close failure becomes a visible exception" is covered on the exception side (`link_closure_failed` + `close_payment_link` retry) but the legacy mark-paid action does not open one yet — that is a one-line call to `openException` once the flag is on and the migration applied.
3. **Migration ledger numbering.** 0062 and 0065 are numbered as assigned; 0063 belongs to another task and 0064 (service activations) is the sibling p4 migration. `0065.activation_id` and `0062.arrangement_id` have no FKs by design; add them in a later migration once 0059 / 0064 are confirmed applied.
4. **`invoices.type` enum** is still `build_milestone | one_off` (+ `care_plan` from a later migration). Obligation kinds `handover_fee`, `service_period`, `grow_item` have no invoice-type equivalent; issuing those obligations as `invoices` rows needs an additive enum value in a separate migration.
5. **Tax mapping is the caller's input.** Nothing here decides VAT (18.8): the actions take a `TaxSnapshot` and `PENDING_TAX` is the safe default. `legacy_no_tax` on backfilled obligations records what the legacy rail did, not a policy.
6. **Inline `"use server"`** is used so the modules export pure functions alongside actions. If a client component ever imports these modules directly, move the actions into a `"use server"` file that re-exports them; nothing imports them today.
7. `isUuid` is exported from `obligations.ts` and reused by `exceptions.ts` (both owned) rather than duplicated; a shared helper elsewhere would be cleaner but is outside the owned files.

## How to try it

1. Tests: `pnpm -C apps/web exec vitest run tests/obligations.test.ts tests/reconciliation.test.ts`.
2. Read the migrations top to bottom; each header is the review checklist (purpose, deviations, backfill, equivalent protection, rollback).
3. In a scratch server component or a REPL-style test, call `planBuildMilestones` with an Order Form's accepted fee and a three-way split and inspect `rows` and `notes`; call `obligationBalance` with a mix of `payment` / `refund` / `credit` allocations; call `suggestMatch` with a bank receipt and a few open obligations and read `evidence`.
4. With `OPS_V2_FLAGS` unset, call any action from a server context and confirm it returns `{ ok: false, reason: "flag_off" }` without a database round trip (the flag check runs immediately after `requireStaff()`).
5. Do **not** set the flag on an environment whose database has not had 0062 / 0065 applied; the actions would fail at the first `from('billing_obligations')` with a Postgres error, which they report as `db_error` without side effects.
