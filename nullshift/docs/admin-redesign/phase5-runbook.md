# Phase 5 — Operations runbook for the admin redesign (flags off)

Date: 17 September 2026 · Task `p5-readiness` · Brief §12.4, §14.2, §15 Phase 5, §17.5. Companion to `docs/OPERATIONS.md` (legacy loops) and `docs/admin-redesign/phase5-pilot-checklist.md` (approvals).

Nothing in this runbook is active in production today: `OPS_V2_FLAGS` is unset, migrations 0057–0065 are NOT APPLIED, and every redesign route renders fixtures. The runbook describes how each area behaves once its flag is on, how to turn it off, what to watch and what to do when something goes wrong.

## 1. Flags per area

`OPS_V2_FLAGS` is a comma-separated server-side env var (`apps/web/lib/flags.ts`). Unknown names are ignored. A flag is read on every request, so changing the env var and redeploying (Vercel: env change + redeploy, or a new deployment) is the whole switch. There is no database-stored flag and no client-supplied override.

## 2. How to disable

1. **One area**: remove its name from `OPS_V2_FLAGS`, redeploy. Every action returns `{ ok: false, reason: "flag_off" }` before touching the database; pages fall back to fixtures / read-only. Data written while the flag was on stays in its tables untouched (see §7).
2. **Everything**: set `OPS_V2_FLAGS=` (empty) or delete the variable. Production behaviour is then byte-for-byte the legacy paths: the GoCardless webhook's first line is `if (flagOn("integrationWorkers")) …`, the ops-worker cron answers `{ ok: true, skipped: "flag_off" }`, `planChoiceOpenV2` becomes `planChoiceOpen`.
3. **Stop the worker only** (keep the inbox capturing): remove `integrationWorkers` — this also stops capture. There is no separate "pause outbound" register yet (the Automations page's pause control is inert). To stop outbound work without losing events, the interim procedure is: remove the cron entry from `apps/web/vercel.json` and redeploy, leaving the flag on so events are still captured; the sweep resumes when the cron returns. Record this in `audit_log` by hand (action `ops.worker_paused`, reason).
4. **Provider side**: disabling a flag never cancels a collection already submitted to GoCardless or an invoice already created in Xero. "A local pause is not a promise that provider payments have stopped" — use the provider dashboard for that, then record the compensating action (§6).

## 4. Stale-integration detection

"Stale" means our record no longer matches the provider or accounting system. The redesign never reconciles on page load (Phase 0 §8 #7); staleness is detected by these explicit paths:

- **Mandates**: `mandates.last_provider_sync_at` and `raw_status` are written only after a resource fetch. A mandate whose `last_provider_sync_at` is older than the newest `integration_events` row for the same `resource_ref` is stale — the event was captured but processing failed; the sweep retries it. Manual check: `select m.id from mandates m join integration_events e on e.resource_ref = m.mandate_ref and e.provider = m.provider and e.environment = m.environment where e.received_at > coalesce(m.last_provider_sync_at, 'epoch')`.
- **Xero invoice / payment links**: an obligation in `issued`/`part_paid` whose invoice has no `xero_invoice_id` after the `xero.create_invoice` operation succeeded, or a `payment_allocations` row without `evidence.xero_payment_id` after `xero.allocate_payment` succeeded, is stale. The handlers recover by lookup (reference match) before creating, so a retry is safe (`safe_retry_op` = `xero_create_invoice` / `xero_allocate_payment`).
- **Provider payments vs collections**: a `service_activations` row `active` with no `provider_payments` row in the period after `provider_confirmed_charge_date` + provider lead time → open `failed_collection` for review; do not assume failure from silence.
- **Environment drift**: a sandbox event carrying a live ref (or the reverse) is refused and lands as unmatched money in the sandbox environment; `GOCARDLESS_ENVIRONMENT` decides the processor's environment. Check the value matches the webhook endpoint that is configured at GoCardless before enabling.
- **Legacy mirror**: with `integrationWorkers` on, legacy subscription rows are still cancelled/marked past_due exactly as today; `recordCarePlanPayment` still mints the `care_plan` invoice. If a legacy tenant's `subscriptions.status` disagrees with the GoCardless dashboard, the legacy path is the one to inspect first.
- **Baseline drift on the protected clients**: run `legacy-invariants.sql` after every apply and after enabling any flag; diff against the stored baseline.

## 5. Dead-letter ownership

- A dead letter is created only by the worker after `max_attempts` (default 8; backoff 1, 2, 4 … min, capped at 6 h) or immediately for a permanent failure (unknown kind, rejected/unconfigured provider, gate missing, unsafe payload).
- Every dead letter opens **one** `finance_exceptions` row (unique per `(kind, subject columns)` while open) with the sanitised `last_error`, the `correlation_id`, `external_ref` = the operation's idempotency key, and a `safe_retry_op` when one exists (`xero.*` → `xero_outage`; `gocardless.schedule_activation` → `missing_activation_gate`, no safe retry; `gocardless.cancel_pending` → `duplicate_warning`, urgent; `notify` → `other`).
- **Owner**: `finance_exceptions.owner` is free text (no capability model yet). Rule for the pilot: the person who enabled the flag owns every exception until reassigned with `assignException` (audited). Unowned `urgent` rows are the first thing checked each morning (Daily loop in `docs/OPERATIONS.md`).
- **Resolution** requires `resolution_evidence` (trigger-enforced); a resolved exception cannot be reopened — open a new one. `attempts` is append-only. Retrying is `proposeExceptionRetry`: it records the proposal and returns the worker operation; nothing executes until a person enqueues it, and the operation's `movesMoney` is `false` by construction (`retryNeverCollects`).
- **Never** resolve a `duplicate_warning` by editing amounts or deleting rows; see §6.

## 6. Financial compensation procedure (never a database rollback that erases history)

Applies to any wrong charge, double collection, refund, chargeback, or an invoice that should not have been issued. History is append-only: the obligation, the provider payment, the allocations and the exception stay; correction is a new, typed, approved action.

1. **Freeze**: open (or find) the `finance_exceptions` row, set `severity = 'urgent'`, assign an owner, and record the facts in `attempts` (what happened, provider ids by fingerprint, amounts, dates). If a collection is still pending at the provider, enqueue `gocardless.cancel_pending` (recorded as cancelled only when the provider confirms); if it is already submitted, the exception says closing a payment link is insufficient.
2. **Establish the truth from the provider**, not from our last event: fetch the payment / mandate / invoice resource. Record the fetched state in the exception.
3. **Decide the compensating action with a second person** (until 18.11 exists: any other staff member, named in the attempt entry): refund, credit note, re-issue, or write-off. No automatic refund exists (`automaticRefund: false`); no write-off without approval (`writeOff: false`, `requiresApproval: true`).
4. **Execute at the provider or in Xero by hand** (there is no refund handler in the outbox on purpose), then **record it as a typed row**: a `provider_payments` row of kind `refund` / `chargeback` / `bank_return` / `credit` with the provider's id and evidence, and a `payment_allocations` row of the same kind against the **same obligation**. The balance functions (`obligationBalance`) then show net paid, credits, remaining and any overpayment; nothing is hidden behind "paid".
5. **Accounting**: enqueue `xero.allocate_payment` only for kind `payment`; refunds and credit notes are recorded in Xero by hand and referenced in the exception's `resolution_evidence` (Xero credit note id fingerprint). The allocate handler refuses non-payment kinds by design.
6. **Client communication**: a stubbed `notify` operation exists only for dedupe; send the actual notice from the mailbox and record the message id in the evidence.
7. **Resolve** the exception with evidence (`resolveException`): what was wrong, what the provider shows now, what was refunded / credited, who approved. Then add the case to the pilot log.
8. **Forbidden**: `UPDATE`/`DELETE` on `provider_payments`, `payment_allocations`, `billing_obligations`, `mandates`, `service_activations`, `finance_exceptions`, `integration_*` or `audit_log` to "tidy up"; editing an accepted schedule's snapshot; re-running a migration's backfill; restoring a database backup to undo a payment. Legacy invoice rows for the protected clients are never touched by any compensation for a new-model client.

## 7. Rolling back the UI without corrupting new records

- **UI first, data never**: turning a flag off hides the writes and routes but leaves every row. Rows written under a flag are inert with the flag off: no legacy path reads `billing_obligations`, `service_arrangements`, `mandates`, `service_activations`, `integration_*` or `finance_exceptions`; `invoices.obligation_id` and `subscriptions.activation_id/arrangement_id/environment` are unread by legacy code; `order_forms.commercial_version` defaults to `v1` and legacy readers ignore it.
- **Do not drop tables to "clean up" a failed pilot**. The rollback DDL in each migration header is for a database that never went live with the flag; after real records exist, keep the tables and the history and disable the flag.
- **Partial rollback order** (if one area must go while others stay): `billingActivation` and `integrationWorkers` together first (they share tables), then `acceptanceGate`, `commercialV2` / `calculator`, `workIntake`. `newShell` is independent.
- **Legacy paths resume exactly**: GoCardless webhook creates the subscription on `billing_requests.fulfilled` again (the very behaviour the brief retires — so a pilot mandate that arrives after the flag is turned off will be activated the old way; cancel the pilot's pending billing request at the provider first).
- **In-flight operations**: a `leased` outbox row whose worker is gone expires and is claimable again; with the flag off nothing claims it. On re-enable, `attempts` continues from where it was (bounded). Nothing is duplicated because every handler is keyed by idempotency and recovers by lookup.
- **Preview deployments** can run any flag against a **branch database** with 0057–0065 applied; never point a live GoCardless or Xero credential at a flagged preview.
- **After any rollback** run `legacy-invariants.sql` for the three protected tenants and diff against the baseline.
