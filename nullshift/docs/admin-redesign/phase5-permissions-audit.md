## 3. Redesign controls that hold regardless of role (verified in code)

- **Every mutation is a server action** that calls `requireStaff()` (staff) or the portal membership check (client) **before** reading the flag, refuses under `ns_client_preview`, uses the caller's RLS client for the write, and calls `logAudit` / `logAuditAsService`: `next/quotes/actions.ts`, `next/agreements/actions.ts`, `lib/work/actions.ts`, `lib/nextActions/actions.ts`, `lib/delivery/actions.ts`, `lib/billing/obligations.ts`, `lib/billing/exceptions.ts`.
- **Tenant is never taken from the browser**: `createQuoteDraft` copies it from the opportunity; schedule actions from the arrangement row; `setNextAction` verifies the project belongs to the tenant; `createObligationsFromOrderForm` verifies the project belongs to the form's tenant; mandate tenant comes from our own records (`resolveMandateOwner`), never provider metadata.
- **Database-side duplicates of the code rules**: author ≠ approver trigger (0057), frozen-content triggers (0057, 0059), second-person CHECKs (0059), one clean acceptance per scope (0060), allocation ceiling trigger with `FOR UPDATE` (0062), one live activation per arrangement and the environment/tenant guard trigger (0064), append-only attempts and resolve-needs-evidence (0065).
- **SECURITY DEFINER functions** (the dry-run lists them): `portal_update_checklist_task`, `portal_update_handover_task` (0060, `revoke from public, anon`, grant to `authenticated`, check `auth.uid()`, membership, `owner_kind = 'client'`, forbid waiver states); `payment_allocations_guard_amount` (0062, trigger function, revoked from public/anon); `integration_operations_claim` (0063, revoked from public/anon/authenticated, granted to `service_role`). All set `search_path = public`. `supersede_service_arrangement` (0059) is SECURITY INVOKER on purpose so the staff policy applies.
- **Client-safe projections**: `service_schedules_client` / `handover_schedules_client` (0059) are `security_barrier` views filtered by `is_member_of` that omit reviewer ids, IP/UA, catalogue refs and internal columns; the estimator's `toClientView` strips rates, hours, costs, floors, targets and margins (tested).
- **Service-role scope**: with the flags on, service-role writes are limited to the webhook inbox / worker (0062 `provider_payments`, 0063, 0064 mandates, 0065 exceptions opened by the worker) and to `logAuditAsService`. No redesign page renders with the service client.

## 4. Gaps (ordered by risk), with the decision that unblocks each

1. **No capability model** — every staff member is a financial administrator (Phase 0 N3; brief §12.5 "introduce explicit capabilities"). Unblock: decision 18.11, then a `staff_capabilities` (or programme-role style) table copied from `lib/soc2/guard.ts`, with `requireCapability('finance.approve_collection')` layered on `requireStaff()`. Until then, "approver ≠ author" is the only separation and it is by user, not by role.
2. **AAL-blind writes** — MFA is a layout redirect; a server action or API route accepts an aal1 session with a TOTP factor (N2/N3). Unblock: cherry-pick `a426c87` (N-a), then make `requireStaff()` refuse `aal1` when `nextLevel = aal2`. Do not weaken MFA to test the redesign (brief §12.5).
3. **Legacy admin actions without `requireStaff`** — eleven client-hub actions and `openLead` rely on RLS alone (N3). Not touched by the redesign; must be fixed before `newShell` replaces the legacy chrome.
4. **Client roles are one role** — signatory / project / billing admin (brief §5.10, §12.5) do not exist; `client_member` is never minted; the legacy portal accept bypasses `is_tenant_admin` (N4). Unblock: decision on portal roles (18.11 / 18.12), then a membership flag set, then switch `build_acceptances_client_insert` and `clientSignatory()` to it.
5. **`audit_log` is client-readable** and has no before/after, reason or correlation id (Phase 0 §3). The redesign writes richer metadata (reasons, `consent_to_amount: false`, idempotency keys) into that same client-readable table. Unblock: a staff-only audit read policy or a separate internal audit table before any finance flag is on for a real tenant.
6. **`newShell` has no consumer** — the flag exists in `flags.ts` but nothing reads it; the prototype is reachable by URL for any staff member. Harmless (fixtures only), but the eventual cut-over must gate the shell behind it, and the legacy `AdminNav` must keep working until then.
7. **Open redirects** on `?next=` (N12) and `deleteClient` hard-delete without a legacy guard (N11) are pre-existing and untouched.
8. **Staff visibility of the inbox/outbox** requires server code with the service client (0063 has no policies). Acceptable now; a read-only staff policy belongs with item 1.
9. **Protected files / signed links** (brief §12.5): `rendered_snapshot_path` (0059) and `signed_artifact_path` (0030) are paths into the private contracts bucket; no redesign code signs URLs yet. When it does, links must be tenant-scoped and time-bounded.
10. **`ADMIN_EMAILS` remains load-bearing** — the allowlist self-provisions a staff membership on GET (an inherited side effect the Phase 0 report documents). Retire only after every staff user has a membership and MFA.

## 5. What this audit did not do

No live query of `memberships`, `soc2_programme_roles` or `auth.users`; no check of who currently holds `ADMIN_EMAILS`; no test of the RLS policies against a database (`packages/db/src/rls.test.mjs` skips without `SUPABASE_DB_URL`). Those are the first items in the pilot checklist.
